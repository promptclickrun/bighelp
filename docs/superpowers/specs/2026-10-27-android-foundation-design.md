# Android foundation

The Android app lives in `android/` in this repository, written in Kotlin with Jetpack Compose. It talks directly to the selected Hermes dashboard, using `docs/NATIVE_TRANSPORT.md` and its chapters as the integration contract. The Apple targets and notification services remain independently buildable.

## First milestone

Build a reproducible Android debug APK and a pure JVM Hermes module. The module owns endpoint validation, bounded atomic wire decoding, explicit connection ownership, readiness and capability gates. Its tests consume the repository's shared wire vectors directly. The app provides the AI data agreement, connection setup, a sessions list, agents, short Settings and an explicitly labeled demo mode. Live operations are offered only as their implementation and acceptance tests become available. Unsupported sign-in methods and uncertain outcomes stay visible and never trigger fallback or mutation replay.

Use `app.bighelp.android` as the development application ID, with `.debug` on debug builds. This reserves nothing on Google Play; confirm the release identity before the first upload. Minimum Android API is 26; compile and target API are 36. Credentials belong in Android Keystore protected storage, excluded from backups and logs. No host request is sent before consent. HTTPS uses ordinary certificate validation; private HTTP requires explicit opt-in and endpoint validation. No credentialed redirects or ambient cookies.

The first app milestone checks only public `/api/status` discovery. It does not collect credentials, save a sign-in, open a gateway or send a live turn. A discovered host is labeled as found, never connected. Keystore persistence arrives with authenticated connection support; the first milestone persists only consent and nonsecret preview preferences.

## Boundaries

`android/hermes` is Kotlin/JVM and owns protocol policy without Android dependencies. `android/app` owns platform storage, lifecycle, screens and demo composition. The pure module exposes typed endpoint and frame models. Readiness, authenticated health and exclusive submission are separate facts. A dispatched mutation without a receipt is uncertain, not failed, and is never automatically repeated. Session runtime IDs and durable stored IDs remain separate.

The initial foundation is not full Android parity. Browser PKCE, reconnect/replay, durable submit recovery, attachments, live voice, groups, phone tools, FCM, Code mode and store release each require their own acceptance evidence. There are no default agent jobs, cloud sign-up dependency or production service deployments.

## Evidence

Run all 55 shared wire vectors and generated byte/count/depth boundaries, endpoint trust tests and scripted readiness/ownership tests. Build the APK and exercise demo controls in light and dark on a dedicated Android emulator if the platform is available. Record JVM, scripted HTTP/WebSocket, emulator, disposable Hermes host and physical-device evidence separately. Account registration may require the maintainer's direct sign-in, identity verification and payment; private information never enters this public repository.
