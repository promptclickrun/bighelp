# Loopdy Link source provenance

This service is maintained in the canonical `promptclickrun/loopdy-ios` repository.

Its initial `src`, `test`, migration and Wrangler configuration content was imported from `promptclickrun/loopdyai` commit `cdf92faea79d83aafc7e61b18685dc562f69120c`, path `services/link`. The predecessor remains archived and is not a development or deployment prerequisite. The Apache-2.0 license is retained here.

The shared TypeScript compiler settings and `Scripts/check-relay.mjs` originate from the same commit. The package command path uses this repository's existing case-sensitive `Scripts` directory. No production database, credentials, or runtime state was copied.

Use the pinned pnpm 9.15.0 toolchain: `pnpm install --frozen-lockfile`, `pnpm test`, and `pnpm check` from this directory. Tests use `wrangler.test.jsonc`, an isolated local Workers runtime configuration that must never be deployed. `wrangler.jsonc` describes the existing production service; importing this source does not deploy or modify that service.

BuzzKit identity cutover has ordered external release dependencies, and `wrangler deploy` does not apply D1 migrations. Before any Worker code rollout, apply the already-released, retirement-only `0007_retire_account_notifications.sql` to the existing production `ACCOUNTS` database and verify that `notification_account_scope_retirements` exists. Do not edit `0007` after it has been applied. Then apply `0008_notification_revocation_fences.sql` and verify—after the `0007` readback—that `notification_installation_revocation_cleanup` and `notification_device_revocations` exist. Finally apply `0009_notification_account_installations.sql` and verify that `notification_account_installations` exists. Use the pinned Wrangler configuration from this directory, for example `pnpm wrangler d1 migrations apply loopdy-link-accounts --remote --config wrangler.jsonc`, followed by a remote read-only `sqlite_master` query for all four table names; do not continue if any ordered migration or table readback is missing. Only after `0007`, `0008`, and `0009` are applied in that order and verified may the Worker candidate roll out. Next rotate the production tenant's identity secret in BuzzKit, update the Worker's `BUZZKIT_IDENTITY_SECRET` secret, and set `BUZZKIT_IDENTITY_SECRET_GENERATION` to `notification-instance-v2` as a secret binding. Do not deploy this Worker or set the generation marker before all three ordered migrations and the provider rotation are confirmed. Link rejects identity issuance, sends, readiness reads, and subscriber deletion when the marker is missing or different. This is necessary because BuzzKit validates an issued identity hash only with the tenant-wide secret; deleting one subscriber cannot invalidate a hash cached by an older client.
